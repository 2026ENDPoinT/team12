# 결정 기록

길찾기 개선 작업([routing-spec.md](routing-spec.md))에서 정한 사항을 기록합니다. 최신 결정이 위에 옵니다.

## 2026-11-12 · 미래관 실내 지도·AR 길안내 통합 (명세 Phase 7)

사용자가 "구조·방향성·사용자 편의·로딩 시간·휴대폰 확인을 고려해 판단해서 넣어 달라"고 위임해서 아래처럼 정했다.

- **통합 방식: 별도 페이지 `dist/indoor/`**. v6 단독 HTML(3.5MB, CDN three)을 `src/indoor/`의 모듈(모델·안내·화면·AR)로 옮겨 esbuild로 묶었다. 캠퍼스 앱 번들을 키우지 않고, 미래관을 누른 사람만 도면을 받는다. 캠퍼스 앱은 미래관 대화상자의 링크 두 개만 바꿨다(`CAMPUS.interior.indoorUrl`, `arUrl`).
- **v6에서 그대로 쓴 것**: 도면 GLB, 층 데이터, 걷기 격자, 0.45m 격자 다익스트라. `scripts/extract-mirae.py`로 `data/mirae/mirae.glb`·`mirae.json`을 꺼냈다(base64를 빼서 약 1MB 줄어듦).
- **경로에 더한 것**: 엘리베이터 연결("계단 없이" 모드), 문이 여러 개인 호실은 가까운 문으로 도착, 목적지가 아닌 방 통과에 4배 비용, 시야가 트인 점만 남겨 경로선 정리, 같은 계단실을 층참만 지나 이어 오르면 한 단계로 안내.
- **빠진 것**: v6의 가우시안 실사 보기는 `splats.json`이 비어 있어 넣지 않았다. 데이터가 생기면 다시 붙인다.
- **실외 ↔ 실내 연결**: 1~3층 도면을 `data/seoultech.json` 미래관 외곽선에 회전·이동 탐색으로 맞췄다(회전 99.5°, 겹침 점수 0.93). 그 결과 캠퍼스 경로의 미래관 도착 노드 `futureDoor`가 도면의 1층 로비 계단 앞(1.82, 6.0)과 1m 안에서 맞아서, 이 지점을 실내 출발점 "1층 로비 출입구"로 정했다. 캠퍼스에서 `?from=futureDoor`로 넘어온다. 지하 1층 유리문 출입구도 실내 출발점으로 넣었다. 둘 다 `verification_status: "candidate"`(현장 확인 전)이다.
  - 명세의 "한 번의 `findRoute`로 정문 → 강의실" 통합은 아직 하지 않았다. 실외 경로는 로비 출입구에서 끝나고, 실내 경로가 거기서 이어진다.
  - `data.mjs`에 표시된 미래관 출입구 3곳(서측·북동측·동측)은 도면의 바깥 문과 맞지 않았다. 서측은 118호 안쪽으로 떨어진다. 현장 확인이 필요하다.
- **AR 위치 인식: 사진 비교 + 센서**. 촬영 사진 1087장(`sv.json`의 카메라 자세 포함)을 수평 기준 원통 띠(방위 92° × 고도 40°, 2°/칸)로 펴서 `ar-index.bin`(977KB)으로 저장했다(`scripts/build-ar-index.py`).
  - 휴대폰 화면도 자이로 중력 방향으로 같은 규칙에 맞춰 펴고, 띠 위를 밀며 정규화 상관을 비교해 위치와 방향을 함께 구한다.
  - 계산은 Web Worker에서 한다. 층은 계단·엘리베이터 근처에서만 바뀌게 했다(층마다 비슷한 복도가 겹쳐 있어서).
  - WebXR은 iPhone Safari가 지원하지 않아서 쓰지 않았다.
- **정확도(영상 프레임 583개, 사진 사이 시각으로 측정)**
  - 휴대폰 센서를 쓰는 추적: 3m 이내 96%, 중앙값 0.25m, 방향 오차 중앙값 2.4°.
  - 센서가 없는 데모 영상 추적: 3m 이내 80%.
  - 한계: 같은 날 같은 동선이라 실제 사용보다 낙관적이다. 촬영 동선 밖이나 조명·가구가 바뀐 곳에서는 위치를 못 찾을 수 있다. 휴대폰 카메라 화각은 65°로 가정했다(`?fov=`로 바꿀 수 있음).
- **데모 영상**: `room.mp4`(544MB)는 커밋하지 않는다. 위치 인식이 가장 안정적인 구간(프레임 12380~13700, 로비 → 108호, 정확도 97%)을 960×540 H.264 4.2MB `data/mirae/demo.mp4`로 잘라 "AR 길안내 데모"에 쓴다.
- **용량**
  - 사진은 표시용으로 480×270로 줄여 15MB로 만들었다. 안내 단계 썸네일과 미리 걷기에 필요한 것만 그때그때 받는다.
  - 실내 첫 화면에서 받는 것은 JS 약 680KB(gzip 약 170KB), 도면 2.5MB, 층 데이터 200KB다.
  - AR 인덱스(1MB)는 AR을 켤 때만 받는다.
- **휴대폰 확인**: 카메라·센서는 HTTPS에서만 동작한다. 같은 와이파이에서 시험할 수 있게 `npm run dev:phone`(자체 서명 인증서, 0.0.0.0)을 추가했다.

## 2026-11-11 · 정문 위치는 지금 그대로 둠

- **현황**: 정문 위치가 두 군데 있다. 그래프 노드 `gate`(-146.6, 432.7)는 `prepare-campus.py`가 만든 기준점이고, `MAIN_GATE`(-233, 216)는 팀이 표시한 정문으로 지도 라벨과 출발지 목록의 "정문"에 쓰인다.
- **결정**: 코드를 바꾸지 않는다. 사용자에게 보이는 정문은 이미 `MAIN_GATE` 하나다. `gate` 노드를 쓰는 홈 미리보기 경로는 CSS로 숨겨져 있어 보이지 않는다. `gate` 노드는 신고·경로 테스트의 고정 기준점으로 유지한다.
- **나중에**: 홈 미리보기를 다시 보이게 하면 출발점을 `MAIN_GATE.entry`로 맞춘다.

## 2026-11-11 · 좌표 변환식을 SMASH 원본과 같게 통일

- **결정**: 위경도 ↔ 미터 변환을 `src/geo.mjs`의 `toScene`, `toLngLat` 두 함수로 모으고, SMASH-SEOULTECH `tools/build_campus.py`와 같은 위도 보정 계수를 쓴다. 기존 `gpsToCampus`(geo.mjs)와 `campusToGps`(gis.mjs)는 이 두 함수를 부르는 이름으로 남긴다.
- **이유**: 지도 데이터는 SMASH가 이 계수로 만든 미터 좌표다. 기존 고정 계수(111132, 111320)는 캠퍼스 끝에서 약 0.6m 어긋났다. OSM 원본 모서리로 확인한 결과 SMASH 식은 0.06m 이내로 맞는다.
- **명세와 다른 점**: 명세의 `src/geo/coords.ts` 대신 기존 `src/geo.mjs`를 쓴다. 저장소가 TypeScript가 아닌 JS(ESM)이기 때문이다.
- **남은 검증**: 명세 Phase 0 완료 기준(구글맵 건물 모서리 3곳이 지도 위 같은 모서리와 5m 이내)은 실제 세계와 지도 데이터의 차이를 보는 것이라, 팀이 구글맵 좌표를 제공해야 확인할 수 있다.

## 2026-11-11 · 데이터 이름 규칙은 팀 GIS 양식을 따름

- **결정**: 새로 추가하는 속성 이름은 명세 3장 대신 `src/gis.mjs`와 `data/team-survey-template.geojson`의 양식을 따른다.

  | 명세 3장 | 사용하는 이름 |
  | --- | --- |
  | `source: "osm" \| "manual" \| "report"` | `source_kind: "public_gis" \| "team_input" \| "generated"` |
  | `verified: boolean` | `verification_status: "candidate" \| "reviewing" \| "verified" \| "rejected" \| "expired"` |
  | `type` (간선·노드 종류) | `feature_type`: `entrance`, `sidewalk`, `stairs`, `building_passage` |

- **이유**: 팀 GIS 양식이 이미 코드·테스트·빌드에 들어가 있어서, 이름을 하나로 유지하는 편이 혼란이 적다.

## 2026-11-11 · 좌표 저장 방식: 내부는 미터, 조사·교환은 위경도

- **결정**: 지도 렌더링과 경로 계산은 기존 `data/seoultech.json`의 미터 좌표(캠퍼스 원점 기준, +x 동쪽, +z 남쪽)를 그대로 쓴다. 팀이 조사해 넣는 데이터(출입구, 인도, 계단, 건물 관통)는 위경도(EPSG:4326) GeoJSON(`data/team-survey-template.geojson` 양식)으로 저장하고, 불러올 때 `toScene`으로 미터로 바꿔 그래프에 합친다.
- **이유**: 기존 화면·경로·신고 코드를 바꾸지 않아도 되고, 조사 데이터는 원점이 바뀌어도 안전하며 외부 도구·서버(PostGIS)와 바로 주고받을 수 있다.
- **기존 데이터**: `data/seoultech.json`은 자동 생성 데이터로 두고 손으로 고치지 않는다. 팀 조사 데이터는 별도 파일에 덧붙인다.

## 2026-11-11 · 팀 main 병합 충돌 정리
