# 결정 기록

길찾기 개선 작업([routing-spec.md](routing-spec.md))에서 정한 사항을 기록합니다. 최신 결정이 위에 옵니다.

## 2026-11-12 · 코드에 적힌 출입구 후보 19곳 삭제, 초록 점은 등록 출입구로

- **결정**: `src/data.mjs`에 좌표로 적혀 있던 1차 출입구 후보 19곳을 지운다. 경로 계산에 쓰이지 않았고, 위치가 최대 13m 어긋나 엉뚱한 벽에 붙은 것도 있었다. 출입구는 편집기로 다시 등록한다.
- **초록 점**: 지도의 초록 점 표시는 남기고, 등록 출입구(`team-survey.json`)를 그린다. 그래서 초록 점은 경로 계산에 실제로 쓰이는 문이다. 편집기에서 바꾸면 바로 다시 그린다. 등록 전에는 초록 점이 없다.
- **같이 바뀐 곳**: 지도 카드 문구 "출입구 후보 N" → "등록 출입구 N", GIS 내보내기의 출입구도 등록 출입구로 바뀌고 `verification_status`는 출입구의 실제 값을 따른다. 테스트용 시험 좌표는 `tests/fixtures.mjs`로 옮겼다.
- **자동 생성 문 규칙(재확인)**: 조사한 출입구가 있는 건물은 그 문들만 쓰고 자동 생성 `*Door`는 뺀다. 자동 생성 문은 "외곽선과 길이 가장 가까운 점"이라 함께 두면 항상 가장 가까운 문으로 뽑혀 실제 문 등록이 무의미해지기 때문이다. 자동 생성 문 자리가 실제 문이면 그 자리에도 출입구를 등록한다.

## 2026-11-12 · 조사 데이터 편집기

- **불러오기 방식**: `src/editor/index.js`를 별도 파일 `dist/editor.js`(약 25KB)로 빌드한다. 주소에 `?edit=1`이 있을 때만 `src/edit-mode.js`가 불러오고, 지도·캠퍼스 데이터·경로 계산은 `window.__saiEditor`로 넘겨받아 다시 내려받지 않는다. 일반 화면에서는 `editor.js`를 아예 불러오지 않는다. `dist/editor.js`는 빌드 결과라 `.gitignore`에 넣었다.
- **도구**: 보기(편집 끔), 선택(고치기·삭제), 출입구(벽 5m 안 클릭 → 벽 위로 붙임), 관통(같은 건물 출입구 두 개), 길·계단(점 여러 개, 기존 길 3m 안이면 붙임).
- **저장 흐름**: 지도 클릭 → 저장 전 미리보기(경로 다시 계산, 편집 전 경로는 회색 점선, 거리 변화 표시) → 저장 또는 취소. 저장한 내용은 브라우저에 임시 저장(`sai:seoultech:survey-draft:v1`)되어 새로고침해도 남는다. 되돌리기(Ctrl+Z), 모두 되돌리기, 불러오기, 내보내기(`team-survey.json` 다운로드)를 둔다. 내보낸 파일을 `data/team-survey.json`에 넣고 커밋해야 모두에게 반영된다.
- **지도 쪽 변경**: 편집 중에는 지도 클릭을 편집기로 넘기고, 건물 이름표·출입구 후보 점이 클릭을 가로채지 않게 한다. 경로 그리기는 편집 중인 그래프의 노드를 받는다. 한 지점을 위에서 내려다보는 `focusTop`을 추가했다.
- **아직 안 한 것**: 점을 끌어서 옮기기는 없다. 지우고 다시 넣는다.

## 2026-11-12 · 건물 출발·도착 시 가장 가까운 출입구 자동 선택 (명세 Phase 2 일부)

- **결정**: 건물을 출발지나 도착지로 고르면, 그 건물의 출입구 노드 전부를 후보로 두고 가장 가까운 문으로 경로를 계산한다. `routing.mjs`(다익스트라)는 바꾸지 않고, `src/route-target.mjs`의 `routeBetween`이 후보 문들을 거리 0으로 잇는 가상 출발·도착점을 붙여 한 번만 계산한다.
- **후보 문**: 팀이 조사한 출입구가 있으면 그것만 쓰고, 자동 생성 `*Door`는 뺀다. 없으면 기존처럼 자동 생성 입구나 건물 중심에서 가장 가까운 노드를 쓴다(`placeEntries`).
- **이유**: 출입구를 조사해 넣어도 도착지가 `futureDoor` 하나로 고정되어 있으면 경로가 바뀌지 않는다. 미래관 후보 출입구 3곳으로 시험하면 정문 → 미래관이 664m에서 652m(서측 출입구)로 바뀐다.
- **아직 안 한 것**: 명세 Phase 2의 출발지 연결(GPS·클릭 위치를 가장 가까운 간선 위의 점으로 투영)은 별도로 한다. 지금 GPS는 여전히 가장 가까운 노드에 붙는다.

## 2026-11-12 · Phase 1 범위와 순서

- **순서**: 디버그 오버레이 → 합치기(팀 조사 파일 → 그래프) → 자동 검사 → 편집 모드. 명세는 편집 모드가 먼저지만, 합치기가 있어야 조사 데이터가 경로에 반영되므로 앞당긴다. 합치기는 원래 Phase 2·3에 속하는 기능이다.
- **조사 파일**: `data/team-survey.json`. 내용은 팀 GIS 양식(`team-survey-template.geojson`)과 같은 위경도 GeoJSON FeatureCollection이다. 확장자를 `.json`으로 한 이유는 Node(테스트)와 esbuild(빌드)가 `.geojson`을 JSON으로 바로 읽지 못하기 때문이다.
- **합치는 시점**: 앱이 열릴 때 `src/data.mjs`가 `seoultech.json`과 조사 파일을 읽어 합친다. `seoultech.json`은 바꾸지 않는다.
- **합치는 순서 (11-12 수정)**: 길·계단 → 출입구 → 관통. 처음에는 출입구를 먼저 넣었는데, 기존 길이 닿지 않는 벽(예: 미래관 남서쪽 오목한 벽)의 문은 팀이 문 앞까지 길을 그려도 붙지 못했다. 길을 먼저 넣으면 그 길에 문이 붙는다. 길 끝이 기존 길에 안 닿아도 결국 문 등 다른 항목과 이어지면 경고하지 않는다. 편집기는 붙지 못하는 항목을 저장 전에 알려 준다.
- **기존 길에 붙이는 방식**: 가장 가까운 간선에 수선을 내린 점에서 간선을 둘로 자르고 연결한다. 연결선이 건물을 지나면 다음 간선을 쓴다. 끝점 1m 안이면 자르지 않고 그 노드를 쓴다. 자른 점 id는 조사 항목 id에서 만들어 매번 같은 결과가 나온다.
- **신고 보존**: 간선이 잘려 간선 id가 바뀌어도, 저장된 클릭 좌표로 가장 가까운 간선을 다시 찾아 신고를 유지한다.
- **편집 결과 저장**: 브라우저에 임시 저장하고, "내보내기"로 받은 파일을 커밋한다. DB는 Phase 5에서 다시 검토한다.
- **검사 기준**: 경로를 틀리게 만드는 경고(연결 안 된 섬, 건물 관통, 중복 노드)는 캠퍼스 전체 0건. 끊긴 길은 데모 경로 주변만 0건이고, 나머지는 표시만 한다.
- **편집기 구조**: 같은 저장소의 `src/editor/`에 두고 별도 파일(`editor.js`)로 빌드한다. 주소에 `?edit=1`이 있을 때만 불러오므로 일반 화면과 다운로드 크기는 바뀌지 않는다.
  - 예외: 그래프 디버그 오버레이(`src/graph-overlay.js`)는 Three.js로 그려야 해서 앱 본체에 넣었다. 수 KB이고 `?edit=1`에서 켤 때만 실행된다. 토글과 범례는 `src/edit-mode.js`에 있다.

## 2026-11-12 · 조사 데이터 입력 항목 단순화

- **출입구**: 이름과 "현장 확인함" 체크만 받는다. 새로 찍으면 `verification_status: "candidate"`, 체크하면 `"verified"`다. 계단 없이 진입 가능 여부는 받지 않는다.
- **건물 관통**: 출입구 두 개와 복도 길이만 받는다. 계단 여부와 개방 시간은 받지 않고, 관통 경로는 항상 열려 있다고 본다. 그래서 명세 Phase 3의 "닫힌 시간에는 관통 제외"와 6장 "개방·닫힌 시각에 다른 경로" 테스트 케이스는 하지 않는다.
- **길·계단**: 종류는 인도(`sidewalk`)와 계단(`stairs`) 두 가지다. 경사로는 원래 데이터와 팀 양식에 없고, 경로 계산에서 인도와 같으므로 따로 두지 않는다.
- **제외 상태**: `rejected`, `expired` 항목은 그래프에 넣지 않는다. 편집기에서는 이 상태를 고르지 않고, 없는 문은 삭제한다.

## 2026-11-11 · 정문 위치는 지금 그대로 둠

- **현황**: 정문 위치가 두 군데 있다. 그래프 노드 `gate`(-146.6, 432.7)는 `prepare-campus.py`가 만든 기준점이고, `MAIN_GATE`(-233, 216)는 팀이 표시한 정문으로 지도 라벨과 출발지 목록의 "정문"에 쓰인다.
- **결정**: 코드를 바꾸지 않는다. 사용자에게 보이는 정문은 이미 `MAIN_GATE` 하나다. `gate` 노드를 쓰는 홈 미리보기 경로는 CSS로 숨겨져 있어 보이지 않는다. `gate` 노드는 신고·경로 테스트의 고정 기준점으로 유지한다.
- **나중에**: 홈 미리보기를 다시 보이게 하면 출발점을 `MAIN_GATE.entry`로 맞춘다.

## 2026-11-11 · 좌표 변환식을 SMASH 원본과 같게 통일

- **결정**: 위경도 ↔ 미터 변환을 `src/geo.mjs`의 `toScene`, `toLngLat` 두 함수로 모으고, SMASH-SEOULTECH `tools/build_campus.py`와 같은 위도 보정 계수를 쓴다. 기존 `gpsToCampus`(geo.mjs)와 `campusToGps`(gis.mjs)는 이 두 함수를 부르는 이름으로 남긴다.
- **이유**: 지도 데이터는 SMASH가 이 계수로 만든 미터 좌표다. 기존 고정 계수(111132, 111320)는 캠퍼스 끝에서 약 0.6m 어긋났다. OSM 원본 모서리로 확인한 결과 SMASH 식은 0.06m 이내로 맞는다.
- **명세와 다른 점**: 명세의 `src/geo/coords.ts` 대신 기존 `src/geo.mjs`를 쓴다. 저장소가 TypeScript가 아닌 JS(ESM)이기 때문이다.
- **남은 검증**: 명세 Phase 0 완료 기준(구글맵 건물 모서리 3곳이 지도 위 같은 모서리와 5m 이내)은 실제 세계와 지도 데이터의 차이를 보는 것이라, 팀이 구글맵 좌표를 제공해야 확인할 수 있다.

## 2026-11-11 · 데이터 이름 규칙은 팀 GIS 양식을 따름

- **결정**: 새로 추가하는 속성 이름은 명세 3장 대신 `src/gis.mjs`와 `data/team-survey-template.geojson`의 양식을 따른다.

  | 명세 3장 | 사용하는 이름 |
  | --- | --- |
  | `source: "osm" \| "manual" \| "report"` | `source_kind: "public_gis" \| "team_input" \| "generated"` |
  | `verified: boolean` | `verification_status: "candidate" \| "reviewing" \| "verified" \| "rejected" \| "expired"` |
  | `type` (간선·노드 종류) | `feature_type`: `entrance`, `sidewalk`, `stairs`, `building_passage` |

- **이유**: 팀 GIS 양식이 이미 코드·테스트·빌드에 들어가 있어서, 이름을 하나로 유지하는 편이 혼란이 적다.

## 2026-11-11 · 좌표 저장 방식: 내부는 미터, 조사·교환은 위경도

- **결정**: 지도 렌더링과 경로 계산은 기존 `data/seoultech.json`의 미터 좌표(캠퍼스 원점 기준, +x 동쪽, +z 남쪽)를 그대로 쓴다. 팀이 조사해 넣는 데이터(출입구, 인도, 계단, 건물 관통)는 위경도(EPSG:4326) GeoJSON(`data/team-survey-template.geojson` 양식)으로 저장하고, 불러올 때 `toScene`으로 미터로 바꿔 그래프에 합친다.
- **이유**: 기존 화면·경로·신고 코드를 바꾸지 않아도 되고, 조사 데이터는 원점이 바뀌어도 안전하며 외부 도구·서버(PostGIS)와 바로 주고받을 수 있다.
- **기존 데이터**: `data/seoultech.json`은 자동 생성 데이터로 두고 손으로 고치지 않는다. 팀 조사 데이터는 별도 파일에 덧붙인다.
