## 2026-11-13 · 실내 안내 문구 정확도 개선, 엘리베이터 탑승 화면

- **문제**: 안내 목록의 거리·방향·단계가 실제 경로와 맞지 않았다(예: 로비 → 228호에서 두 번의 회전이 "오른쪽 방향으로 37m" 하나로 뭉침).
- **원인 1**: 경로가 벽에 붙어 계산돼, 선 다듬기(시야 검사)가 복도에서 실패하고 0.45m 계단 모양 점이 그대로 남았다.
- **원인 2**: 안내 생성이 "짧은 구간의 꺾임은 합친다" 규칙으로 0.45m 조각 위의 실제 90° 회전을 버렸다. 계단·엘리베이터에서 나올 때 바라보는 방향 기준도 없었다.
- **고친 것**
  - 경로 탐색에 벽 옆 칸 비용(1.7배·1.2배)을 더해 복도 가운데로 걷게 했다.
  - 다듬기는 진행 방향 좌우 0.25m 여유를 검사하고, RDP 단순화(0.35m)로 남은 지그재그를 정리한다.
  - 회전 판단은 꺾인 점의 앞뒤 3m 방향으로 하고, 3m 안의 연속 꺾임은 합쳐 전체 각도로 판단한다(35° 미만은 직진).
  - 계단은 경사로의 첫·마지막 구간, 엘리베이터는 문 ↔ 칸 중심 방향으로 진입·진출 방향을 정해 "왼쪽에 있는 계단으로", "계단에서 나와 오른쪽으로"를 안내한다.
  - 회전 지점 3.5m 안의 호실을 기준으로 붙인다("222호 앞에서").
  - 단계마다 경로상 거리(s)를 저장해 지도 번호 표시, 미리 걷기, AR 진행률이 같은 기준을 쓴다.
  - 테스트: 안내한 좌·우가 경로 기하와 맞는지 6개 경로에서 확인한다.
- **엘리베이터**
  - 미리 걷기는 문 닫힘 → 층 표시 증가 → 도착음 → 문 열림 장면을 재생한다.
  - AR은 문 앞에 오면 "3F 버튼을 누르세요" 탑승 화면을 띄우고, 도착 층에서 위치가 다시 잡히면 문이 열리며 안내를 이어 간다. 위치를 못 잡을 때는 "내렸어요" 버튼으로 넘어간다.
  - 지도에서 층을 바꾸면 카메라가 층 높이만큼 오르내리고 큰 층 표시가 나온다.
- **도착 지점**
  - 경로가 방 안이나 문틀 가운데가 아니라, 문이 놓인 벽에서 복도 쪽으로 0.7m 떨어진 문 앞에서 끝난다(공간이 좁으면 0.4~1.1m).
  - 도착 안내의 좌·우와 AR 도착 문구("문은 왼쪽")는 문 위치를 기준으로 하고, 미리 걷기는 마지막 1.2m에서 문을 바라보도록 돌아선다.
  - 테스트: 모든 목적지(100곳)의 도착점이 방 밖, 문에서 0.3~1.3m 안에 있는지 확인한다.
- **사용성·안정성**
  - 안내 목록과 지도 번호를 연결해, 목록을 누르면 그 지점으로 날아간다.
  - 미리 걷기에 재생·정지, 이전·다음 단계, 1·2·4배속을 넣었다.
  - 음성 안내 켜기·끄기(설정 기억), 최근 검색, 출발·도착 바꾸기, 경로 공유 링크(`?from=&to=&mode=`)를 추가했다.
  - AR에 화면 꺼짐 방지(Wake Lock)와 다른 앱 전환 뒤 위치 다시 찾기를 넣었다. 신뢰도가 낮을 때는 바닥 경로를 숨기고, 확실히 벗어났을 때만 재탐색한다.
  - 카메라를 켜지 못했을 때 오류 창 버튼이 동작하지 않던 버그를 고쳤다.

## 2026-11-12 · 미래관 실내 지도·AR 길안내 통합 (명세 Phase 7)

사용자가 "구조·방향성·사용자 편의·로딩 시간·휴대폰 확인을 고려해 판단해서 넣어 달라"고 위임해서 아래처럼 정했다.

- **통합 방식: 별도 페이지 `dist/indoor/`**. v6 단독 HTML(3.5MB, CDN three)을 `src/indoor/`의 모듈(모델·안내·화면·AR)로 옮겨 esbuild로 묶었다. 캠퍼스 앱 번들을 키우지 않고, 미래관을 누른 사람만 도면을 받는다. 캠퍼스 앱은 미래관 대화상자의 링크 두 개만 바꿨다(`CAMPUS.interior.indoorUrl`, `arUrl`).
- **v6에서 그대로 쓴 것**: 도면 GLB, 층 데이터, 걷기 격자, 0.45m 격자 다익스트라. `scripts/extract-mirae.py`로 `data/mirae/mirae.glb`·`mirae.json`을 꺼냈다(base64를 빼서 약 1MB 줄어듦).
- **경로에 더한 것**: 엘리베이터 연결("계단 없이" 모드), 문이 여러 개인 호실은 가까운 문으로 도착, 목적지가 아닌 방 통과에 4배 비용, 시야가 트인 점만 남겨 경로선 정리, 같은 계단실을 층참만 지나 이어 오르면 한 단계로 안내.
- **빠진 것**: v6의 가우시안 실사 보기는 `splats.json`이 비어 있어 넣지 않았다. 데이터가 생기면 다시 붙인다.
- **실외 ↔ 실내 연결**: 1~3층 도면을 `data/seoultech.json` 미래관 외곽선에 회전·이동 탐색으로 맞췄다(회전 99.5°, 겹침 점수 0.93). 그 결과 캠퍼스 경로의 미래관 도착 노드 `futureDoor`가 도면의 1층 로비 계단 앞(1.82, 6.0)과 1m 안에서 맞아서, 이 지점을 실내 출발점 "1층 로비 출입구"로 정했다. 캠퍼스에서 `?from=futureDoor`로 넘어온다. 지하 1층 유리문 출입구도 실내 출발점으로 넣었다. 둘 다 `verification_status: "candidate"`(현장 확인 전)이다.
  - 명세의 "한 번의 `findRoute`로 정문 → 강의실" 통합은 아직 하지 않았다. 실외 경로는 로비 출입구에서 끝나고, 실내 경로가 거기서 이어진다.
  - `data.mjs`에 표시된 미래관 출입구 3곳(서측·북동측·동측)은 도면의 바깥 문과 맞지 않았다. 서측은 118호 안쪽으로 떨어진다. 현장 확인이 필요하다.
- **AR 위치 인식: 사진 비교 + 센서**. 촬영 사진 1087장(`sv.json`의 카메라 자세 포함)을 수평 기준 원통 띠(방위 92° × 고도 40°, 2°/칸)로 펴서 `ar-index.bin`(977KB)으로 저장했다(`scripts/build-ar-index.py`).
  - 휴대폰 화면도 자이로 중력 방향으로 같은 규칙에 맞춰 펴고, 띠 위를 밀며 정규화 상관을 비교해 위치와 방향을 함께 구한다.
  - 계산은 Web Worker에서 한다. 층은 계단·엘리베이터 근처에서만 바뀌게 했다(층마다 비슷한 복도가 겹쳐 있어서).
  - WebXR은 iPhone Safari가 지원하지 않아서 쓰지 않았다.
- **정확도(영상 프레임 583개, 사진 사이 시각으로 측정)**
  - 휴대폰 센서를 쓰는 추적: 3m 이내 96%, 중앙값 0.25m, 방향 오차 중앙값 2.4°.
  - 센서가 없는 데모 영상 추적: 3m 이내 80%.
  - 한계: 같은 날 같은 동선이라 실제 사용보다 낙관적이다. 촬영 동선 밖이나 조명·가구가 바뀐 곳에서는 위치를 못 찾을 수 있다. 휴대폰 카메라 화각은 65°로 가정했다(`?fov=`로 바꿀 수 있음).
- **데모 영상**: `room.mp4`(544MB)는 커밋하지 않는다. 위치 인식이 가장 안정적인 구간(프레임 12380~13700, 로비 → 108호, 정확도 97%)을 960×540 H.264 4.2MB `data/mirae/demo.mp4`로 잘라 "AR 길안내 데모"에 쓴다.
- **용량**
  - 사진은 표시용으로 480×270로 줄여 15MB로 만들었다. 안내 단계 썸네일과 미리 걷기에 필요한 것만 그때그때 받는다.
  - 실내 첫 화면에서 받는 것은 JS 약 680KB(gzip 약 170KB), 도면 2.5MB, 층 데이터 200KB다.
  - AR 인덱스(1MB)는 AR을 켤 때만 받는다.
- **휴대폰 확인**: 카메라·센서는 HTTPS에서만 동작한다. 같은 와이파이에서 시험할 수 있게 `npm run dev:phone`(자체 서명 인증서, 0.0.0.0)을 추가했다.

## 2026-11-12 · 신고 단계·사유·사진 필수, 건물 공사 표시, 건물 번호

- **신고 단계**: 접수(지도에 안 보임) → 같은 구간에 신고 3건 이상이면 주의(노란색) + 관리자 검토 알림 → 관리자가 확정하면 경고(빨간색)이고 그때만 우회 경로. 노란색은 경로를 바꾸지 않는다. 이전에는 1건부터 노란색이었다.
- **3건 세는 법**: 같은 기기(`reporter_device_id`)가 같은 구간을 여러 번 신고해도 1건으로 센다. 한 사람이 혼자 노란색을 만들지 못하게 하려는 것이다.
- **사유 3가지**: 공사 중(`construction`), 장애물·통제(`blocked`), 기타 직접 입력(`other` + `reason_note`, 100자까지, 비우면 신고 불가).
- **사진 필수**: 사진이 있어야 신고 버튼이 켜진다. 업로드가 실패하면 신고도 저장하지 않는다(이전에는 사진 없이 저장했다). 카메라는 `<input capture="environment">`로 휴대폰 뒷카메라를 바로 연다. 앱 안 카메라 화면(getUserMedia)은 만들지 않는다. Storage 경로에는 파일 이름 대신 확장자만 쓴다(한글 파일 이름 오류 방지).
- **건물 공사**: 관리자 화면에서 건물·시작일·종료일·메모로 등록하고 해제한다. Supabase `building_works` 표. 지도에는 건물 위 🚧 표시만 하고, 누르면 공사 기간이 3초 보였다가 사라진다. 종료일이 지나면 자동으로 안 보인다. **경로 계산에는 반영하지 않는다**(관통 경로도 그대로).
- **건물 번호**: 학교 공식 캠퍼스맵 PDF(https://www.seoultech.ac.kr/intro/map)의 건물번호순 목록을 `src/buildings.mjs`에 넣고 이름표를 "60 미래관"처럼 표시한다. 공식 목록에 없는 건물(어학원, 창조관, 동아리실 등)과 `전문대학원(36호관)`(공식 36번은 공사 중인 수연관)은 번호 없이 이름만 쓴다.
- **확정 해제**: 관리자 화면 "확정된 구간"에서 "해제 · 공사 끝남"을 누르면 그 구간 신고를 모두 지워 경로를 다시 연다. 확정·반려·해제는 `edge_id`가 아니라 신고 행 id로 처리한다(조사 데이터로 구간이 쪼개지면 화면의 구간 id와 DB `edge_id`가 달라서). RLS에 막혀 0건이 처리되면 실패 알림을 띄운다(이전에는 조용히 넘어갔다). DB 규칙은 `supabase/2026-11-12-release-confirmed.sql`.
- **DB 변경**: `supabase/2026-11-12-reasons-and-building-works.sql`을 Supabase SQL Editor에서 한 번 실행해야 한다. 공사 등록·삭제는 지금 시연용 관리자 잠금과 같은 수준(anon 키 허용)이라, 관리자 로그인을 붙일 때 정책을 좁힌다.

## 2026-11-12 · 코드에 적힌 출입구 후보 19곳 삭제, 초록 점은 등록 출입구로

- **결정**: `src/data.mjs`에 좌표로 적혀 있던 1차 출입구 후보 19곳을 지운다. 경로 계산에 쓰이지 않았고, 위치가 최대 13m 어긋나 엉뚱한 벽에 붙은 것도 있었다. 출입구는 편집기로 다시 등록한다.
- **초록 점**: 지도의 초록 점 표시는 남기고, 등록 출입구(`team-survey.json`)를 그린다. 그래서 초록 점은 경로 계산에 실제로 쓰이는 문이다. 편집기에서 바꾸면 바로 다시 그린다. 등록 전에는 초록 점이 없다.
- **같이 바뀐 곳**: 지도 카드 문구 "출입구 후보 N" → "등록 출입구 N", GIS 내보내기의 출입구도 등록 출입구로 바뀌고 `verification_status`는 출입구의 실제 값을 따른다. 테스트용 시험 좌표는 `tests/fixtures.mjs`로 옮겼다.
- **자동 생성 문 규칙(재확인)**: 조사한 출입구가 있는 건물은 그 문들만 쓰고 자동 생성 `*Door`는 뺀다. 자동 생성 문은 "외곽선과 길이 가장 가까운 점"이라 함께 두면 항상 가장 가까운 문으로 뽑혀 실제 문 등록이 무의미해지기 때문이다. 자동 생성 문 자리가 실제 문이면 그 자리에도 출입구를 등록한다.

- **지도 쪽 변경**: 편집 중에는 지도 클릭을 편집기로 넘기고, 건물 이름표·출입구 후보 점이 클릭을 가로채지 않게 한다. 경로 그리기는 편집 중인 그래프의 노드를 받는다. 한 지점을 위에서 내려다보는 `focusTop`을 추가했다.
- **아직 안 한 것**: 점을 끌어서 옮기기는 없다. 지우고 다시 넣는다.

## 2026-11-12 · 건물 출발·도착 시 가장 가까운 출입구 자동 선택 (명세 Phase 2 일부)

- **결정**: 건물을 출발지나 도착지로 고르면, 그 건물의 출입구 노드 전부를 후보로 두고 가장 가까운 문으로 경로를 계산한다. `routing.mjs`(다익스트라)는 바꾸지 않고, `src/route-target.mjs`의 `routeBetween`이 후보 문들을 거리 0으로 잇는 가상 출발·도착점을 붙여 한 번만 계산한다.
- **후보 문**: 팀이 조사한 출입구가 있으면 그것만 쓰고, 자동 생성 `*Door`는 뺀다. 없으면 기존처럼 자동 생성 입구나 건물 중심에서 가장 가까운 노드를 쓴다(`placeEntries`).
- **이유**: 출입구를 조사해 넣어도 도착지가 `futureDoor` 하나로 고정되어 있으면 경로가 바뀌지 않는다. 미래관 후보 출입구 3곳으로 시험하면 정문 → 미래관이 664m에서 652m(서측 출입구)로 바뀐다.
- **아직 안 한 것**: 명세 Phase 2의 출발지 연결(GPS·클릭 위치를 가장 가까운 간선 위의 점으로 투영)은 별도로 한다. 지금 GPS는 여전히 가장 가까운 노드에 붙는다.

## 2026-11-12 · Phase 1 범위와 순서

- **순서**: 디버그 오버레이 → 합치기(팀 조사 파일 → 그래프) → 자동 검사 → 편집 모드. 명세는 편집 모드가 먼저지만, 합치기가 있어야 조사 데이터가 경로에 반영되므로 앞당긴다. 합치기는 원래 Phase 2·3에 속하는 기능이다.
- **조사 파일**: `data/team-survey.json`. 내용은 팀 GIS 양식(`team-survey-template.geojson`)과 같은 위경도 GeoJSON FeatureCollection이다. 확장자를 `.json`으로 한 이유는 Node(테스트)와 esbuild(빌드)가 `.geojson`을 JSON으로 바로 읽지 못하기 때문이다.
- **합치는 시점**: 앱이 열릴 때 `src/data.mjs`가 `seoultech.json`과 조사 파일을 읽어 합친다. `seoultech.json`은 바꾸지 않는다.
- **합치는 순서 (11-12 수정)**: 길·계단 → 출입구 → 관통. 처음에는 출입구를 먼저 넣었는데, 기존 길이 닿지 않는 벽(예: 미래관 남서쪽 오목한 벽)의 문은 팀이 문 앞까지 길을 그려도 붙지 못했다. 길을 먼저 넣으면 그 길에 문이 붙는다. 길 끝이 기존 길에 안 닿아도 결국 문 등 다른 항목과 이어지면 경고하지 않는다. 편집기는 붙지 못하는 항목을 저장 전에 알려 준다.
- **기존 길에 붙이는 방식**: 가장 가까운 간선에 수선을 내린 점에서 간선을 둘로 자르고 연결한다. 연결선이 건물을 지나면 다음 간선을 쓴다. 끝점 1m 안이면 자르지 않고 그 노드를 쓴다. 자른 점 id는 조사 항목 id에서 만들어 매번 같은 결과가 나온다.
- **신고 보존**: 간선이 잘려 간선 id가 바뀌어도, 저장된 클릭 좌표로 가장 가까운 간선을 다시 찾아 신고를 유지한다.
- **편집 결과 저장**: 브라우저에 임시 저장하고, "내보내기"로 받은 파일을 커밋한다. DB는 Phase 5에서 다시 검토한다.
- **검사 기준**: 경로를 틀리게 만드는 경고(연결 안 된 섬, 건물 관통, 중복 노드)는 캠퍼스 전체 0건. 끊긴 길은 데모 경로 주변만 0건이고, 나머지는 표시만 한다.
- **편집기 구조**: 같은 저장소의 `src/editor/`에 두고 별도 파일(`editor.js`)로 빌드한다. 주소에 `?edit=1`이 있을 때만 불러오므로 일반 화면과 다운로드 크기는 바뀌지 않는다.
  - 예외: 그래프 디버그 오버레이(`src/graph-overlay.js`)는 Three.js로 그려야 해서 앱 본체에 넣었다. 수 KB이고 `?edit=1`에서 켤 때만 실행된다. 토글과 범례는 `src/edit-mode.js`에 있다.

## 2026-11-12 · 조사 데이터 입력 항목 단순화

- **출입구**: 이름과 "현장 확인함" 체크만 받는다. 새로 찍으면 `verification_status: "candidate"`, 체크하면 `"verified"`다. 계단 없이 진입 가능 여부는 받지 않는다.
- **건물 관통**: 출입구 두 개와 복도 길이만 받는다. 계단 여부와 개방 시간은 받지 않고, 관통 경로는 항상 열려 있다고 본다. 그래서 명세 Phase 3의 "닫힌 시간에는 관통 제외"와 6장 "개방·닫힌 시각에 다른 경로" 테스트 케이스는 하지 않는다.
- **길·계단**: 종류는 인도(`sidewalk`)와 계단(`stairs`) 두 가지다. 경사로는 원래 데이터와 팀 양식에 없고, 경로 계산에서 인도와 같으므로 따로 두지 않는다.
- **제외 상태**: `rejected`, `expired` 항목은 그래프에 넣지 않는다. 편집기에서는 이 상태를 고르지 않고, 없는 문은 삭제한다.

## 2026-11-11 · 정문 위치는 지금 그대로 둠

- **현황**: 정문 위치가 두 군데 있다. 그래프 노드 `gate`(-146.6, 432.7)는 `prepare-campus.py`가 만든 기준점이고, `MAIN_GATE`(-233, 216)는 팀이 표시한 정문으로 지도 라벨과 출발지 목록의 "정문"에 쓰인다.

## 2026-11-11 · 좌표 변환식을 SMASH 원본과 같게 통일

- **결정**: 위경도 ↔ 미터 변환을 `src/geo.mjs`의 `toScene`, `toLngLat` 두 함수로 모으고, SMASH-SEOULTECH `tools/build_campus.py`와 같은 위도 보정 계수를 쓴다. 기존 `gpsToCampus`(geo.mjs)와 `campusToGps`(gis.mjs)는 이 두 함수를 부르는 이름으로 남긴다.
- **이유**: 지도 데이터는 SMASH가 이 계수로 만든 미터 좌표다. 기존 고정 계수(111132, 111320)는 캠퍼스 끝에서 약 0.6m 어긋났다. OSM 원본 모서리로 확인한 결과 SMASH 식은 0.06m 이내로 맞는다.
- **명세와 다른 점**: 명세의 `src/geo/coords.ts` 대신 기존 `src/geo.mjs`를 쓴다. 저장소가 TypeScript가 아닌 JS(ESM)이기 때문이다.
- **남은 검증**: 명세 Phase 0 완료 기준(구글맵 건물 모서리 3곳이 지도 위 같은 모서리와 5m 이내)은 실제 세계와 지도 데이터의 차이를 보는 것이라, 팀이 구글맵 좌표를 제공해야 확인할 수 있다.

## 2026-11-11 · 데이터 이름 규칙은 팀 GIS 양식을 따름

- **결정**: 새로 추가하는 속성 이름은 명세 3장 대신 `src/gis.mjs`와 `data/team-survey-template.geojson`의 양식을 따른다.

  | 명세 3장 | 사용하는 이름 |
  | --- | --- |
  | `source: "osm" \| "manual" \| "report"` | `source_kind: "public_gis" \| "team_input" \| "generated"` |
  | `verified: boolean` | `verification_status: "candidate" \| "reviewing" \| "verified" \| "rejected" \| "expired"` |
  | `type` (간선·노드 종류) | `feature_type`: `entrance`, `sidewalk`, `stairs`, `building_passage` |

- **이유**: 팀 GIS 양식이 이미 코드·테스트·빌드에 들어가 있어서, 이름을 하나로 유지하는 편이 혼란이 적다.

## 2026-11-11 · 좌표 저장 방식: 내부는 미터, 조사·교환은 위경도

- **결정**: 지도 렌더링과 경로 계산은 기존 `data/seoultech.json`의 미터 좌표(캠퍼스 원점 기준, +x 동쪽, +z 남쪽)를 그대로 쓴다. 팀이 조사해 넣는 데이터(출입구, 인도, 계단, 건물 관통)는 위경도(EPSG:4326) GeoJSON(`data/team-survey-template.geojson` 양식)으로 저장하고, 불러올 때 `toScene`으로 미터로 바꿔 그래프에 합친다.
- **이유**: 기존 화면·경로·신고 코드를 바꾸지 않아도 되고, 조사 데이터는 원점이 바뀌어도 안전하며 외부 도구·서버(PostGIS)와 바로 주고받을 수 있다.
- **기존 데이터**: `data/seoultech.json`은 자동 생성 데이터로 두고 손으로 고치지 않는다. 팀 조사 데이터는 별도 파일에 덧붙인다.
