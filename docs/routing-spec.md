# 사이 캠퍼스 내비게이션 — 길찾기 개선 작업 명세

Nov 11, 2026 · @주인

## 1. 개요

이번 작업의 목표는 **경로 품질**이다. 지도와 GPS는 동작하므로, 길 그래프 데이터와 출발·도착점 연결 방식을 고쳐 "정문에서 강의실 문 앞까지" 실제로 걸을 수 있는 경로를 안내한다.

**현재 동작하는 것**

- Three.js 단독 씬 3D 캠퍼스 지도 (SMASH 저장소 `data/campus.json`, OSM 기반 ODbL 데이터를 과기대 중심 미터 좌표로 변환)
- 다익스트라 최단경로, 길 막힘 신고 후 우회 경로 (신고는 브라우저에만 저장)
- GPS 현재 위치 표시 (실외 오차 약 10m 이내), 이동에 따라 남은 거리와 화살표 갱신

**발견된 문제**

1. 사람이 걸을 수 있는 길이 그래프에 없어서, 카카오맵 경로보다 돌아가는 비효율 경로가 나온다.
2. 건물 출입구 위치가 부정확해서 출발·도착 연결이 어긋난다.
3. 학생들이 실제로 지나다니는 건물 관통 경로가 없어서, 건물을 통과하면 짧은 구간도 건물을 빙 돌아가게 계산된다.

**이번 개선 범위**: 그래프 정비 도구, 출입구 데이터, 건물 관통 간선, 경로 검증, 모드(배리어프리), 신고 DB 공유, GPS 안내 보강, 미래관 실내 연결.

### 작업 방식: 확인 → 질문 → 적용

이 문서의 파일 경로, 데이터 형식, 수치는 기존 코드를 보기 전에 쓴 **제안**이다. Claude Code는 바로 구현하지 말고 아래 순서를 지킨다.

1. **확인**: 각 Phase 시작 시 아래 표의 "코드 확인" 항목을 저장소에서 읽고 요약해 보고한다.
2. **질문**: 코드가 문서의 가정과 다르거나 "사용자 결정" 항목에 닿으면, 차이와 선택지(장단점 포함)를 제시하고 멈춰서 묻는다.
3. **적용**: 답을 받은 뒤에만 구현하고, 결정 내용은 저장소 `docs/decisions.md`에 기록한다.

## 2. 설계 원칙

기존 화면과 다익스트라는 유지하고, 데이터와 연결 로직을 고친다. 갈아엎지 않는다.

- **좌표**: 데이터는 위경도(WGS84)로 저장하고, 렌더링과 거리 계산 직전에만 캠퍼스 중심 미터 좌표로 변환한다. 변환 함수는 `toScene`, `toLngLat` 두 개를 한 모듈에만 두고 모든 코드가 그것만 쓴다. 원점·공식·축 방향은 기존 campus.json 변환과 완전히 같아야 한다.
- **그래프는 데이터, 알고리즘은 코드**: 길 그래프는 JSON 파일로 분리하고, 사람이 편집 도구로 고친다. 알고리즘은 그래프 내용을 몰라도 동작해야 한다.
- **기존 다익스트라 확장**: 새로 짜지 않는다. 비용 함수를 인자로 받게 바꿔서 모드(최단, 배리어프리)와 막힘 제외를 처리한다.
- **출처 표시**: 간선마다 `source`(osm, manual, report)를 기록해 어디서 온 길인지 추적한다. 화면에 ODbL 및 "© OpenStreetMap contributors" 표기를 넣는다.
- **TMAP은 보조**: 캠퍼스 밖 출발 구간과, 우리 경로가 TMAP보다 지나치게 긴 구간을 찾는 검증용으로만 쓴다. 응답을 그래프 데이터로 저장하지 않는다.

## 3. 데이터 모델

길 그래프는 `data/graph/seoultech.json` 하나에 노드와 간선을 담고, 출입구는 노드의 한 종류로 둔다. 건물 관통은 같은 건물 출입구 사이의 간선으로 표현한다.

아래 스키마는 제안안이다. 기존 그래프 형식을 먼저 확인해 차이를 보고하고, 기존 형식을 확장할지 이 스키마로 변환할지 사용자에게 물은 뒤 적용한다.

```ts
type LngLat = [number, number]; // [경도, 위도]

type NodeType = "junction" | "entrance" | "indoor" | "stairs" | "elevator" | "room";

interface GraphNode {
  id: string;
  pos: LngLat;
  type: NodeType;
  buildingId?: string;     // entrance, indoor, room
  floor?: number;          // 실내 노드
  name?: string;           // "미래관 정문", "401호"
  accessible?: boolean;    // entrance: 계단 없이 진입 가능
}

type EdgeType = "footway" | "crossing" | "stairs" | "ramp" | "building_passage" | "indoor" | "vertical";

interface GraphEdge {
  id: string;
  from: string;
  to: string;
  type: EdgeType;
  geometry?: LngLat[];     // 직선이 아닐 때 중간 점
  lengthM: number;         // 자동 계산, 수동 덮어쓰기 허용
  hasStairs: boolean;
  indoor: boolean;
  openHours?: string;      // "07:00-22:00", building_passage에 주로 사용
  source: "osm" | "manual" | "report";
  verified: boolean;
}

interface Blockage {
  id: string;
  center: LngLat;
  radiusM: number;
  reason: "construction" | "blocked";
  reportCount: number;
  expiresAt: string;       // ISO
}
```

**규칙**

- 간선은 양방향으로 해석한다. 일방통행이 필요하면 그때 `oneway` 필드를 추가한다.
- `building_passage` 간선은 같은 `buildingId`의 두 출입구를 잇고, `lengthM`은 실제 통과 거리(복도 길이)로 직접 입력한다.
- 건물 외곽선을 가로지르는 간선은 `building_passage`, `indoor`, `vertical`만 허용한다 (Phase 1 자동 검사).
- 도착지가 건물이면 건물 중심이 아니라 그 건물의 `entrance` 노드 중 하나로 연결한다.

## 4. 작업 단계와 완료 기준

각 단계는 앞 단계가 끝나야 의미가 있다. Phase 0\~4가 이번 문제 해결의 핵심이다.

**Phase 0. 코드 파악과 좌표 통일**

1. 기존 코드에서 그래프 데이터 형식, 다익스트라, 막힘·우회, GPS 표시 코드를 찾아 구조를 정리한다.
2. 위경도 ↔ 미터 변환을 `src/geo/coords.ts` 하나로 모으고, 기존 변환과 결과가 같은지 테스트한다.
3. 기존 그래프 형식과 3장 스키마의 차이를 보고하고, 확장할지 변환할지 사용자에게 확인한 뒤 진행한다.

완료 기준: 구글맵에서 딴 건물 모서리 3곳을 `toScene`으로 찍었을 때 지도 위 같은 모서리와 5m 이내.

**Phase 1. 그래프 디버그·편집 도구**

1. 디버그 오버레이: 노드(종류별 색), 간선(종류별 색), 출입구 라벨을 지도 위에 토글로 표시.
2. 자동 검사 표시: 연결 안 된 섬(connected component), 끝이 끊긴 노드, 1m 이내 중복 노드, 건물 외곽선을 관통하는 일반 간선.
3. 편집 모드: 지도 클릭으로 노드 추가, 두 노드 선택해 간선 추가, 선택 삭제, 속성 편집 패널, JSON 내보내기.
4. 현장 기록 버튼: 현재 GPS 위치를 여러 번 샘플링해 평균값으로 노드 후보 저장 (메모 포함).

완료 기준: 편집 후 내보낸 JSON을 다시 불러오면 같은 그래프가 나오고, 검사 경고 0건.

**Phase 2. 출입구와 출발·도착 연결**

1. 건물마다 실제 출입구를 `entrance` 노드로 등록 (현장 조사 결과 반영).
2. 도착지 연결: 건물 목적지 → 출발지 기준 경로 비용이 가장 작은 출입구로 자동 선택.
3. 출발지 연결: GPS·클릭 위치를 가장 가까운 노드가 아니라 **가장 가까운 간선 위의 점**으로 투영하고, 그 점에서 간선 양 끝으로 임시 연결. 투영선이 건물 외곽선을 지나면 다음 후보 간선 사용.

완료 기준: 테스트 케이스(6장)에서 경로 시작·끝이 건물을 관통하지 않음.

**Phase 3. 누락 길과 건물 관통 경로**

1. 현장 조사로 찾은 누락 보행로를 `footway`로 추가.
2. 건물 관통 경로를 `building_passage`로 추가하고 `openHours` 입력.
3. 경로 계산 시 현재 시각 기준으로 닫힌 관통 간선은 제외.

완료 기준: 테스트 케이스의 경로 길이가 카카오맵·TMAP 대비 1.1배 이하이거나, 관통 경로로 더 짧음.

**Phase 4. 다익스트라 확장 (비용 함수)**

1. `findRoute(start, end, { mode, now, blockages })` 형태로 바꾸고 비용 함수를 분리.
2. 모드: `shortest`(거리), `accessible`(계단 간선 제외, `accessible` 출입구만).
3. 막힘 원 영역과 교차하는 간선 제외.
4. 결과에 구간별 안내 생성: 건물 진입·통과·진출, 계단, 방향 전환.

완료 기준: 두 모드가 같은 그래프에서 다른 경로를 내는 케이스 1개 이상 확인.

**Phase 5. 막힘 신고 DB 공유**

1. 기존 신고 저장 방식을 확인하고, 사용자 확인 후 공유 DB(Supabase 제안)의 `blockages` 테이블로 이전.
2. 20m 이내 기존 신고가 있으면 `reportCount` 증가, `expiresAt` 연장.
3. 안내 중 새 막힘이 남은 경로와 겹치면 현재 위치에서 재계산 + 알림.

**Phase 6. GPS 안내 보강**

1. 현재 위치를 경로선 위로 투영해 표시 (흔들림 감소).
2. 경로에서 25m 이상 3회 연속 이탈 시 재탐색.
3. 녹화한 GPS 궤적을 재생하는 시뮬레이션 모드 (발표장 데모용).

**Phase 7. 미래관 실내 연결**

1. 피난안내도 기반으로 1\~2개 층 실내 노드·간선 작성 (`indoor`, `stairs`, `elevator`, `room`).
2. 층 사이는 `vertical` 간선, 미래관 `entrance` 노드에서 실외 그래프와 연결.
3. 실내 화면은 2D 평면도 + 경로선.

완료 기준: 정문 → 미래관 강의실 문 앞까지 한 번의 `findRoute`로 계산.

**Phase 8 (선택). 가우시안 미리보기**

목적지 주변 가우시안을 별도 뷰어로 전환해 표시, 압축본 사용, 노트북 데모 기준.

## 5. 현장 조사 방법

그래프 품질은 코드보다 현장 데이터에 달려 있다. GPS 오차가 약 10m라서 GPS 값만 믿지 말고 지도 위에서 눈으로 보정한다.

1. **조사 범위 정하기**: 데모 경로(정문 → 미래관)와 테스트 케이스 경로 주변부터. 캠퍼스 전체는 그다음.
2. **출입구 기록**: 출입구 앞에 서서 Phase 1의 현장 기록 버튼으로 위치 저장 → 메모에 건물명, 정문/후문, 계단 유무, 개방 시간 적기 → 나중에 지도에서 건물 외곽선의 문 위치로 끌어서 보정.
3. **누락 길 찾기**: 카카오맵·TMAP 도보 경로와 우리 경로를 같은 출발·도착으로 비교해서 차이 나는 구간을 직접 걸어보고, 실제로 걸을 수 있으면 간선 추가.
4. **건물 관통 경로**: 학생들이 실제로 통과하는 건물과 입구 쌍, 대략 통과 시간, 개방 시간을 기록.
5. **계단·경사로**: 배리어프리 모드용으로 계단 구간과 경사로 대체 경로 표시.
6. **사진**: 헷갈리는 출입구와 관통 통로 입구는 사진을 찍어 두기 (안내 카드용).

조사 결과는 편집 도구로 바로 그래프에 반영하고, `source: "manual"`, `verified: true`로 저장한다.

| 배리어프리 | (계단 있는 구간) | (반대편) | `accessible` 모드에서 계단 없음 | 계단 간선 0개 |
| 막힘 우회 | 정문 | 미래관 | 경로 위 막힘 추가 시 우회 | 막힘 영역과 교차 0 |
| 실내 | 정문 | 미래관 강의실 | 실외 → 출입구 → 층 이동 → 호실 | 한 번의 계산 |

**자동 검사** (`npm run check:graph`)

- 연결 안 된 섬 0개, 1m 이내 중복 노드 0개
- 건물 외곽선을 지나는 일반 간선 0개
- 모든 건물에 `entrance` 노드 1개 이상
- 모든 `building_passage` 양 끝이 같은 건물 출입구

**TMAP 비교 스크립트 (선택)**: 캠퍼스 주요 지점 쌍마다 우리 경로 길이와 TMAP 도보 경로 길이를 비교해, 우리 쪽이 1.3배 이상 긴 쌍을 목록으로 출력한다. 누락 길 후보를 찾는 용도이며 TMAP 응답은 저장하지 않는다.

## 7. 우선순위, 데모, 미결정 사항

**우선순위**: Phase 0 → 1 → 2 → 3 → 4 → 7 → 5 → 6 → 8. Phase 0\~4와 7까지 끝나면 "정문에서 강의실 문 앞까지" 데모가 완성된다.

**데모 시나리오**

1. 정문에서 미래관 강의실 검색 → 관통 경로나 지름길을 쓰는 경로 표시, 카카오맵 대비 짧아진 거리 표시
2. 배리어프리 모드 전환 → 계단 없는 경로로 바뀜
3. 경로 위에 공사 신고 → 우회 경로로 갱신
4. 녹화한 GPS 궤적 재생으로 이동 안내 → 미래관 진입 후 층 이동, 호실 도착

**Claude Code 작업 시 지침**

- 1장의 작업 방식(확인 → 질문 → 적용)을 모든 Phase에 적용한다. 문서와 코드가 다르면 문서를 근거로 밀어붙이지 말고 묻는다.
- 기존 화면 구조와 디자인은 바꾸지 않는다. 바꿔야 하면 먼저 묻는다.
- 각 Phase 끝에 완료 기준을 테스트로 확인하고, 그래프 자동 검사를 통과시킨다.

**미결정 사항**

결정이 필요한 항목은 1장 작업 방식의 표에서 한곳으로 관리하고, 결정되면 `docs/decisions.md`에 기록한다.
